## Evaluation in Microsoft Foundry

> Implementation reference. See the [README](../README.md) and
> [architecture overview](architecture.md) for the current framework.

## Purpose

Evaluation answers a simple question:

> **Is the agent behaving well enough to trust, and can we detect regressions when it changes?**

For agentic applications, evaluation is broader than checking whether the final answer sounds good. A useful evaluation system can test:

- final-answer quality
- task completion
- instruction adherence
- tool use
- grounding
- abstention when evidence is missing
- domain-specific business rules
- safety
- latency and cost trade-offs

The important mental model is:

```text
Agent version
    ↓
Evaluation dataset
    ↓
Evaluators
    ↓
Scores + row-level failures
    ↓
Improve prompt/tool/model
    ↓
Re-run the same dataset
```

The trust comes from repeated evidence, not from a few successful playground conversations.

## 1. Three sources of evaluation data

A mature evaluation dataset usually grows from three sources.

### Hand-crafted cases

These encode known product requirements and important edge cases.

Examples for the Contoso Coffee agent:

- exact menu lookup
- price filtering
- budget arithmetic
- semantic recommendations
- missing-information abstention
- hallucination resistance
- scope adherence
- ambiguous requests

These are the most important early cases because humans know what behavior is required.

### Synthetic cases

Foundry can generate synthetic evaluation queries when broader coverage is useful.

Synthetic generation is useful for scale, but should not replace deliberate human-authored cases.

### Production traces

Production traces reveal what users actually ask.

Useful traces should be reviewed and converted into permanent regression cases when they reveal:

- a new failure mode
- a surprising but valid user phrasing
- an unexpected tool path
- a missing requirement
- a recurring ambiguity

The long-term loop is:

```text
Curated cases
     ↓
Release
     ↓
Production traces
     ↓
Interesting failure
     ↓
Add permanent regression case
     ↓
Dataset becomes stronger
```

## 2. Dataset design

A minimal JSONL row can look like:

```json
{"name":"exact_espresso_price","category":"exact_retrieval","query":"How much is an espresso?","ground_truth":"Espresso costs $2.50."}
```

Useful fields:

- `name` — stable test identifier
- `category` — behavior group
- `query` — user input
- `ground_truth` — expected answer or expected behavior
- `source` — optional, for example `handcrafted` or `trace`
- `evaluation_type` — optional, for example `deterministic` or `semantic`

For behavioral tests, `ground_truth` does not need to be exact wording. Describe the contract rather than one exact sentence.

---

## 3. Evaluator families

### Deterministic evaluators

Use code or exact rules. Best for requirements with an objective answer.

Examples:

```text
Expected price = $2.50
Budget total <= $6.00
Forbidden item must not appear
Required JSON field must exist
Off-topic question must not be answered directly
```

Advantages:

- cheap
- repeatable
- explainable
- stable

Limitations:

- weak for open-ended semantic quality

Use deterministic evaluation whenever the requirement can be stated objectively.

### Generic LLM-as-a-judge evaluators

Foundry provides built-in evaluators for dimensions such as:

- coherence
- relevance
- task adherence
- task completion
- intent resolution
- safety dimensions
- agent/tool behavior where supported

These are useful for broad semantic quality.

However, built-in metrics should not automatically be treated as truth. An evaluator can be a poor match for a product requirement.

Example:

```text
User: Who is the president of France?

Product requirement:
Coffee-shop agent must refuse unrelated questions.

A generic task-completion evaluator may penalize the agent
for not answering the user's literal request.
```

The evaluator must match the product contract.

### Custom rubric evaluators

Custom rubrics are often the most useful evaluators for enterprise agents.

Example rubric for the Contoso agent:

```text
Pass only if the response:
1. satisfies the expected behavior,
2. does not invent unsupported menu facts,
3. respects explicit user constraints,
4. abstains when required information is unavailable,
5. stays within the Contoso Coffee scope when appropriate.
```

This lets the evaluator judge semantic behavior against the application's own requirements.

Microsoft Foundry supports custom code-based, prompt-based, and endpoint-based evaluators.

## 4. Field mapping

When evaluating a live Foundry agent against an existing dataset, there are two kinds of fields.

```text
item.*
    = fields in your JSONL dataset

sample.*
    = values generated by the live agent run
```

Typical mapping:

```text
Query            {{item.query}}
Ground truth     {{item.ground_truth}}
Response         {{sample.output_text}}
```

For agent trajectories, Foundry may expose structured output/tool artifacts through generated sample fields.

Do not manually fabricate tool calls in the dataset merely to satisfy an evaluator. If a particular agent tool is not fully supported by an evaluator, changing the JSONL structure may not solve the underlying limitation.

---

## 5. Evaluator selection

Do not select every evaluator in the catalog.

Choose evaluators based on actual failure modes.

For a narrow RAG/menu agent, a reasonable stack may be:

```text
Deterministic checks
    ↓
Exact facts / budgets / forbidden behavior

Custom behavior rubric
    ↓
Groundedness / abstention / scope / constraint-following

Optional generic evaluator
    ↓
Coherence or relevance
```

A useful evaluation result should help answer:

> **What broke, and what should I change?**

---

## 6. Baseline evaluation

A baseline is a stable agent version evaluated against a stable dataset.

Example:

```text
Prompt v2 + GPT-5 + Azure AI Search
             ↓
        40 test cases
             ↓
deterministic + custom rubric evaluators
             ↓
baseline metrics
```

Useful reporting is by category, not only one aggregate number.

Example:

```text
Exact retrieval           100%
Filtering                  98%
Budget constraints         94%
Recommendations            93%
Abstention                100%
Hallucination resistance   92%
Scope adherence           100%
```

Category-level metrics reveal where the agent is fragile.

---

## 7. Regression evaluation

Once a baseline exists, use the **same dataset** after every meaningful change.

Examples:

```text
Prompt v2 vs Prompt v3
GPT-5 vs model-router
Search configuration A vs B
Tool description A vs B
```

Then compare:

- quality
- latency
- token use
- cost
- error rate
- specific category regressions

The key principle:

> **Change one important variable, rerun the same benchmark, and compare.**

## 8. Cloud evaluation from Python

A useful project split is:

```text
Foundry
    ↓
Persisted Prompt Agent
    ↓
Model + instructions + tools

Python
    ↓
Invoke agent
    ↓
Generate results
    ↓
Launch cloud evaluation
```

Your Python harness can own:

- dataset loading
- repeated agent invocation
- deterministic checks
- cloud evaluation submission
- comparison logic
- future CI/CD gates

Foundry can own:

- agent runtime
- evaluator catalog
- judge model execution
- result persistence
- portal visualization

Microsoft recommends cloud evaluation for predeployment testing, larger-scale evaluation, recurring runs, and CI/CD scenarios.

### In this repository

| Concern | Where it lives |
|---|---|
| Regression dataset | `evals/contoso_agent_eval_v3.jsonl` |
| Agent invocation and token capture | `src/foundry_prompt_agent/agent.py` |
| Upload, evaluation run, polling, pass rates, quality gate | `src/foundry_prompt_agent/foundry_eval.py` |
| Orchestration and console output | `scripts/run_evaluation.py` |
| Generated responses for one execution | `evals/results_v3.jsonl` |

Run it with `uv run scripts/run_evaluation.py` from the repository root. The gate enforces `contoso_behavior_rubric >= 0.90` and `contoso_scope_adherence == 1.00` by default, both overridable through `BEHAVIOR_PASS_RATE_THRESHOLD` and `SCOPE_PASS_RATE_THRESHOLD`.

## 9. Agent Optimizer

Agent Optimizer automates part of the improvement loop.

```text
Baseline agent
     ↓
Evaluation dataset
     ↓
Evaluate baseline
     ↓
Generate candidate configurations
     ↓
Evaluate candidates
     ↓
Rank candidates
     ↓
Review and optionally promote winner
```

Possible optimization targets include:

- instructions
- skills
- tool descriptions
- model selection

The optimizer does **not** eliminate the need for a strong dataset or meaningful evaluators.

If the benchmark is too easy, the optimizer has little room to improve. Agent Optimizer is currently a preview capability.

## 10. Scheduled regression evaluation

Scheduled evaluation answers:

> **Does the known benchmark still pass over time?**

Example:

```text
Every week
    ↓
Run the fixed regression dataset
    ↓
Current agent version
    ↓
Same evaluators
    ↓
Compare against baseline
```

This can detect regressions caused by:

- prompt edits
- model changes
- search/index changes
- tool changes
- platform/runtime changes

For a small learning project, weekly is usually enough.

## 11. CI/CD quality gates

Evaluation becomes a release gate when a pipeline can fail on unacceptable quality.

```text
Pull request
    ↓
Run agent evaluation
    ↓
Check thresholds
    ↓
PASS → merge/deploy
FAIL → investigate
```

Example gates:

```text
Behavior rubric >= 95%
Scope adherence == 100%
Hallucination failures == 0
```

Microsoft provides the `microsoft/ai-agent-evals` GitHub Action for offline Foundry agent evaluation inside CI/CD.

The action can:

- invoke Foundry agents against test queries
- use evaluator catalog entries
- compare agent versions
- publish evaluation summaries
- report statistical comparisons

Use Microsoft Entra ID with GitHub OIDC rather than long-lived Azure secrets.

Do not necessarily run expensive LLM evaluations on every commit. Trigger them on meaningful agent changes, pull requests, release branches, or manually.

## 12. Evaluation maturity model

```text
Level 1 — Playground testing
"Does it seem to work?"

Level 2 — Curated evaluation dataset
"Can I repeat the important tests?"

Level 3 — Custom evaluators
"Am I measuring my real product contract?"

Level 4 — Regression comparisons
"Did this change make things better or worse?"

Level 5 — Production trace mining
"What failures did real users discover?"

Level 6 — Scheduled evaluation
"Does known quality remain stable over time?"

Level 7 — CI/CD quality gates
"Can poor agent versions be prevented from shipping?"
```

## Architecture Journal

### What Foundry automates

- live agent invocation
- cloud evaluator execution
- judge-model calls
- evaluator catalog
- evaluation result persistence
- portal visualization
- scheduled evaluation
- Agent Optimizer
- CI/CD integrations

### What we still own

- defining what good means
- representative dataset design
- choosing useful evaluators
- determining thresholds
- interpreting failures
- release decisions
- deciding when a metric is misleading

### What changes with LangGraph?

The evaluation philosophy barely changes.

LangGraph gives more runtime/orchestration control, but the application still needs:

- datasets
- evaluators
- baselines
- regression tests
- production traces
- monitoring
- release gates

Evaluation sits **above the agent framework**.
